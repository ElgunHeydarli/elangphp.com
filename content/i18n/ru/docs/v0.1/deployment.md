# Развёртывание

Приложения Elang работают на стандартном веб-сервере PHP. Этот сайт использует PHP-FPM за Apache и Nginx.

## Подготовка приложения

```bash
composer install --no-dev --prefer-dist --optimize-autoloader
php elang migrate --force
```

Проверьте миграции и создайте резервную копию базы данных перед изменением рабочей среды. Не устанавливайте инструменты разработки в публичный каталог.

## Окружение

Установите `APP_ENV=production`, `APP_DEBUG=false`, HTTPS-адрес в `APP_URL` и сгенерированный `APP_KEY`. Отдельно настройте учётные данные базы данных и почты. Предоставьте процессу PHP доступ на запись только в `storage/` и необходимые расположения базы данных.

## Корневой веб-каталог

Направьте веб-сервер на `public/`. Передавайте несуществующие пути в `index.php`. Apache может использовать включённый `.htaccess`. Типичный блок location для Nginx:

```nginx
location / {
    try_files $uri $uri/ /index.php?$query_string;
}
```

Добавьте блок PHP-FPM, подходящий вашему серверу. Не открывайте доступ к корню проекта, файлам vendor, метаданным Git, секретам или файлам SQLite.

## Существующий виртуальный хостинг

Если панель управления хостингом фиксирует корневой веб-каталог, храните приложение вне него и копируйте в публичный каталог только содержимое `public/`. Настройте точку входа на загрузку закрытого приложения. Скрипт публикации этого сайта следует такой модели.

## После развёртывания

Проверьте ожидаемые страницы и ответы API, изучите серверные журналы и отслеживайте сбои. Сертификаты HTTPS и заголовки безопасности для статических ресурсов следует настраивать на уровне хостинга. Эта предварительная версия не включает автоматическое развёртывание без простоя или управляемый хостинг.

## Письма учётной записи и аутентификация домена

Подтверждение email и восстановление пароля требуют рабочего почтового транспорта. Значение по умолчанию `null://null` намеренно отключает письма учётной записи в производственной среде. Используйте SMTP с аутентификацией, действительным TLS-сертификатом и разрешённым отправителем; `smtps` на порту 465 защищает соединение TLS с самого начала. Имя пользователя и пароль внутри DSN должны быть URL-кодированы. Не отключайте проверку сертификата.

Закрытый файл секрета позволяет не хранить DSN в самом файле окружения:

```dotenv
MAILER_DSN=
MAILER_DSN_FILE=/run/secrets/elang-mailer-dsn
MAIL_FROM=noreply@example.com
```

Указанный файл содержит полный DSN, принадлежит оператору приложения и должен быть доступен для чтения только нужной учётной записи. Непустой `MAILER_DSN` имеет приоритет над `MAILER_DSN_FILE`. Не помещайте учётные данные в Git, чат, снимки экрана или публичный каталог.

Создайте ящик отправителя и проверьте SMTP-аутентификацию. Опубликуйте SPF фактического сервиса отправки, открытый DKIM-ключ почтового сервера и политику DMARC в авторитетной DNS-зоне домена. Перед добавлением записи проверьте существующую политику: несколько политик SPF могут нарушить аутентификацию. Начните с мониторинга DMARC, прежде чем выбирать более строгий режим. Приём письма SMTP-сервером или проверка локального ящика не доказывают доставку внешним провайдерам.

На официальном сайте Elang подтверждённый администратор может просмотреть три подготовленные записи в разделе [интеграций](/admin/integrations#mail-dns). Публикатор Fornex добавляет недостающие записи только для `elangphp.com`, останавливается при конфликте политик и никогда не заменяет и не удаляет существующие записи. API-ключ используется для одного запроса и не сохраняется. Операцию защищают HTTPS, CSRF, права администратора, подтверждение текущего пароля, ограничение запросов и блокировка публикации. При частичном сбое провайдера часть новых записей может остаться; повторная попытка сначала проверяет существующие записи. Распространение публичного DNS и реальную доставку проверяйте отдельно.

## Резервное копирование и проверка восстановления

Копируйте вместе базу данных, закрытые объектные файлы, ключ приложения, подключённые файлы секретов и зашифрованные настройки интеграций. Храните копии вне `public/` с ограниченными правами; защищённая копия должна находиться и за пределами сервера приложения. Без соответствующего ключа шифрования копия базы не восстановит зашифрованные учётные данные, уведомления и проверку аудита.

Используйте инструмент согласованного резервного копирования своей СУБД. Для SQLite установите клиент командной строки и используйте команду онлайн-копирования вместо копирования файла базы во время записи запросов. Подставьте фактический путь к базе в своём развёртывании:

```bash
install -d -m 700 /srv/elang-backups
sqlite3 /srv/elang/storage/database.sqlite ".backup '/srv/elang-backups/elang.sqlite'"
chmod 600 /srv/elang-backups/elang.sqlite
sqlite3 /srv/elang-backups/elang.sqlite 'PRAGMA integrity_check;'
```

Результат проверки целостности `ok` — только первая проверка. Восстановите копию в отдельную базу и закрытый каталог хранилища. Сравните число строк всех таблиц с завершённой резервной копией; проверьте миграции, доступ администратора, содержимое и цепочку HMAC-аудита с соответствующим ключом приложения. Никогда не направляйте учебное восстановление на рабочую базу и не включайте отправку email и webhook в восстановленной среде.

Отдельно отрепетируйте откат версии приложения. Сохраняйте заведомо рабочую версию исходников и её зависимости. Откат исходников не отменяет изменения схемы, доставленные письма и записи в объектном хранилище. Официальный хостинг использует атомарный указатель закрытой версии; другие развёртывания должны самостоятельно обеспечивать смену версии и перезапуск обработчиков. См. [версии и обновления](/docs/v0.1/releases) и [эксплуатацию](/docs/v0.1/observability).
